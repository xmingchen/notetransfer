## A. 稳定性与可用性

### A1 单点依赖：嗅探失效则全线失效（高）

**问题**：v0.1 的抖音通路完全依赖硬编码 CDN 域名关键词与 DOM 行为猜测，且 yt-dlp 已确认失效，没有第三级兜底。

**为什么严重**：付费服务背后有团队持续对抗平台变更，而我们只有一次性写好的正则。方案目标是"长期替代"，但抗变更能力远不如被替代对象。

**修复**：
- `acquire()` 显式实现三级降级，第三级 `via_local_file()` 接受用户手动下载的文件——这是唯一不受平台变更影响的通路
- 域名关键词集中为 `CDN_HINTS` / `DECOY_HINTS` 常量，便于快速调整
- 建议配合定期自检（对固定测试链接跑一遍），失效尽早暴露

### A2 只取 top2 候选流 + 无产出校验（高）

**问题**：`ranked[:2]` 硬编码。`content-length` 在 chunked 编码下常为 0，此时排序几乎只由域名加权决定，同域名多流的相对顺序不确定。若前两名都是视频流，会走进 "video-only" 分支，静默产出无声视频 → 空转写 → 一篇只有截图、没有内容的笔记。

**为什么严重**：这是"看似成功的失败"，最难发现，且污染知识库。

**修复**：
- `via_browser()` 遍历全部候选，以"凑齐一条视频轨 + 一条音频轨"为终止条件
- `cli.main()` 增加质量闸门：空转写 → 退出码 2 拒绝交付，除非显式 `--allow-empty-transcript`
- 无音轨情况写入 `warnings`，调用方可见

### A3 内存缓冲整个视频（高）

**问题**：`f.write(response.body())` 把整个响应读进内存。30MB 无事，1 小时 1080p（1~2GB）会 OOM，且失败发生在下载末期。

**修复**：改用 `curl -sL --fail -o` 分块落盘，附 30 分钟超时。放弃 Playwright 的 `request` API（不支持流式），改为拿到 URL + cookies 后交给 curl。

### A4 无超时上限与并发保护（中）

**问题**：whisper CPU 转写同步阻塞，2 小时视频可能跑 30+ 分钟；连续丢多个链接会启动多个实例抢 CPU，机器卡死。

**修复**：
- `single_run_lock()` 用 `fcntl.flock` 保证串行，冲突时快速失败而非排队堆积
- `--max-duration`（默认 3600s）超长视频直接拒绝并提示如何放宽
- `RunLog.stage()` 记录每阶段耗时，写入 manifest，等待成本可量化

## B. 正确性与数据质量

### B1 图文未真正对齐，图注质量依赖运气（高）

**问题**：抽帧与转写是两条独立时间轴，manifest 里各自列出、无关联。写笔记时只能"看图猜章节"。

**为什么严重**：这一环是方案宣称的核心优势。实测样本恰好是幻灯片式视频（章节与时间线性对应），所以效果好；遇到穿插剪辑、倒叙、口播插片段就会错配。**自信的错误图注比没有图更有害**——它给出了不该有的可信度。

**修复**：
- `context_around(segments, t, window=15)` 提取该时刻前后 15 秒转写文本
- 每个 `Frame` 带 `context` 字段进 manifest，图文关联有据可依
- 找不到重叠区间时退化为最近邻片段，而非留空
- 约定：写笔记时若某帧 context 无法归入任何章节，宁可丢弃不用

### B2 降级通路元数据严重退化（中）

**问题**：嗅探通路用 `re.search(r"@([^@|\-_]{1,30})", title)` 从页面标题猜作者。实测中作者字段其实是人工比对旧笔记才填对的，脚本本身没提取出来。

**为什么是问题**：知识库里错误的元数据会污染后续检索，且难以察觉。

**修复**：
- `_page_meta()` 依次尝试 `og:` 系列、`meta[name=author]`、`article:author`、JSON-LD 的 `author`/`creator`
- 全部失败时**显式置为 `unknown` 并记 warning**，绝不用正则猜测填充
- 时长统一由 ffprobe 补齐并写回 manifest

### B3 转写错字率被低估且纠错无校验（中）

**问题**：small 模型在技术中文上错字密集（向量库→"香凉库"、索引→"锁引"、权限→"全线"、置信度→"知心度"、拒答→"巨达"）。v0.1 靠领域知识手工纠正，但没有机制保证纠对了，也没留下改动痕迹。

**为什么是问题**：换到不熟悉的领域（医学、法律），可能纠反而笔记读起来非常通顺可信——知识库最危险的污染形式。

**修复**：
- `initial_prompt` 注入领域词表（`--glossary` 可覆盖），从源头减少错字
- **始终保留 `transcript.raw.txt`**（未经整理的原始转写），任何纠正都可回溯核对
- `--model medium` 可选；Apple Silicon 上后续可切 MLX-Whisper

### B4 时间戳与帧的静默错位（低）

**问题**：v0.1 用 `zip` 把 ffmpeg `showinfo` 日志的 `pts_time` 列表与排序后的目录列表配对，依赖"顺序一致"假设；任何多余日志行或写入失败都会让映射整体错位，代码用 `t = -1.0` 静默兜底。

**修复**：改为两阶段——先用 `-f null -` 只收集候选时间点，再对保留的时间点逐个 `-ss <精确时间>` 重新截图。文件名由时间戳生成，二者强绑定，不存在顺序假设。

## C. 工程化与可维护性

### C1 硬编码路径与版本号（高）

**问题**：写死 `chromium-1228` 与 macOS 专属路径。Playwright 升级或缓存清理后直接报文件不存在——而这发生在"降级通路"，意味着主通路失效时兜底也没了。

**修复**：`find_chromium()` 运行时探测：环境变量 → glob 匹配 `chromium-*` 取最高 build → 系统 Chrome → PATH 查找。全部失败时给出可执行的修复命令。

### C2 无结构化日志与失败可观测性（中）

**问题**：全靠 `print`；多处 `except Exception: pass` 完全吞掉异常。"看似成功的失败"不留任何告警。

**修复**：
- `RunLog` 记录每阶段名称/耗时/成败/错误摘要，连同 `warnings[]` 写入 manifest
- 移除所有裸 `pass`：非致命异常记 warning，致命异常抛 `PipelineError`
- 写笔记前可读 `manifest.run.warnings`，如实向用户披露"本次无音频""元数据缺失"

### C3 无幂等与截图命名冲突（中）

**问题**：截图命名 `wb_frame_01_t0s.jpg` **不带任何视频标识**。处理第二个视频时会直接覆盖第一个视频已入库的截图，导致已有笔记里的图片悄悄变成别的视频画面——真实的数据丢失。

**修复**：
- 文件名前缀为 `url_slug(url)`（URL 的 SHA1 前 10 位），如 `b7643bd266_03_t112s.jpg`
- `~/.notetransfer/ledger.json` 记录 URL → 工作目录/标题/时间，重复链接返回退出码 3，`--force` 可覆盖

### C4 文档与实现存在偏差（低）

**问题**：文档把"场景检测 + 感知哈希去重"写成核心策略，但实测场景检测 0 命中、实际生效的是等间隔兜底。照抄者会误判。

**修复**：`select_timestamps()` 返回实际使用的策略名，写入 manifest 的 `frame_strategy`；文档以实测命中情况陈述，而非假设主路径可用。同时把阈值改为两级递降（0.25 → 0.12）再退等间隔，提高场景检测的实际命中率。

## D. 合规与风险

### D1 绕过反爬的合规边界未说明（中）

**问题**：通过无头浏览器嗅探绕过技术限制，伪装 UA 并注入 `--disable-blink-features=AutomationControlled`。个人学习用途风险较低，但方案要在公司技术平台分享，被同事在商业场景规模化复用可能触及服务条款甚至法律风险。

**修复**：README 增设「使用边界与合规」，明确限定个人学习、禁批量抓取、建议频率上限（≤10 条/小时）、禁二次分发、企业场景需先做合规评估。

### D2 内容版权与二次使用未标注（低）

**修复**：采集层始终保留原始链接与作者署名；笔记模板 frontmatter 增加用途标注字段（如 `usage: 个人学习存档，勿外传`）。

## E. 成本的完整口径

### E1 "零成本"表述不完整（中）

v0.1 文档强调"边际成本 0"，只比了钱，没比时间与算力。完整口径应为：

| 维度 | 商用同步服务 | notetransfer |
|---|---|---|
| 现金成本 | 每条按积分计费 | 0 |
| 等待时长 | 云端并行，通常更快 | 12 分钟视频约 3~5 分钟（CPU） |
| 本机资源 | 不占用 | 转写期间 CPU 高负载 |
| 一次性磁盘 | 0 | whisper small 约 460MB |
| 调用方额度 | 不涉及 | 整理环节消耗 Agent token |
| 可定制性 | 固定模板 | 完全可控 |
| 隐私 | 内容过第三方服务器 | 全本地 |
| 抗平台变更 | 服务商持续维护 | 需自行维护 |

**结论应是有条件的**：追求速度与省心 → 用商用服务；追求格式可控、隐私、长期零现金成本，且愿意承担维护责任 → 用本项目。单向宣称"完胜"不成立。
